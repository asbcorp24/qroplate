# QROplate ESP32 firmware

ESP32 controller for paid timed equipment access.

## Current MVP flow

1. ESP32 shows a QR code on the 1.54 inch e-paper display.
2. QR contains `device_id`, BLE MAC address and local access code.
3. Flutter app scans the QR and connects to the ESP32 over BLE.
4. App writes the access code to the AUTH characteristic.
5. After successful payment, the app writes the paid duration in seconds.
6. ESP32 stores the end time in NVS, turns the relay ON and counts time using DS3231 RTC.
7. When time expires, ESP32 turns the relay OFF and shows the QR screen again.
8. If ESP32 reboots during an active session, the session is restored from NVS and RTC.

> Important: the current BLE duration command is for bench testing/MVP only. Before real commercial payments, the duration command must be replaced by a server-signed one-time payment token so a user cannot reuse the BLE access code to start the equipment for free.

## Hardware assumed

- MH-ET LIVE / ESP32 Dev Module
- MH-ET LIVE 1.54 inch B/W e-paper, 200x200
- DS3231 RTC module
- relay module

### Wiring

| Module | Signal | ESP32 GPIO |
|---|---|---:|
| E-paper | DIN/MOSI | 23 |
| E-paper | CLK/SCK | 18 |
| E-paper | CS | 5 |
| E-paper | DC | 17 |
| E-paper | RST | 16 |
| E-paper | BUSY | 4 |
| RTC DS3231 | SDA | 21 |
| RTC DS3231 | SCL | 22 |
| Relay | IN | 27 |

Power and ground must be common. Check the relay module input voltage and whether it is active HIGH or active LOW before connecting a real load.

## E-paper revision

`include/config.h` contains `EPD_MODEL`.

- `1` = `GxEPD2_154_D67`, SSD1681, 200x200
- `2` = older `GxEPD2_154` / GDEP015OC1 compatible panel

MH-ET LIVE sold more than one 1.54 inch revision. If the display stays white or shows garbage, switch `EPD_MODEL` and rebuild.

## Device provisioning

Edit `include/config.h` for every physical device:

```cpp
#define DEVICE_ID "DEV-000001"
#define BLE_DEVICE_NAME "QRPAY-000001"
#define DEVICE_ACCESS_CODE "CHANGE_ME"
```

For production, the access code must be unique per unit and generated by the admin system rather than committed to the public repository.

## BLE protocol

Service UUID:

`7a610000-71ce-4a7a-a9d8-6ad4bd36b000`

Characteristics:

| Characteristic | UUID suffix | Operation | Payload |
|---|---|---|---|
| INFO | `0001` | Read | JSON with device id, BLE name and MAC |
| AUTH | `0002` | Write | device access code |
| DURATION | `0003` | Write | paid duration in seconds, decimal text |
| STATUS | `0004` | Read/Notify | JSON status and remaining seconds |

Example bench test sequence:

```text
AUTH write: CHANGE_ME
DURATION write: 60
```

The relay should remain ON for 60 seconds.

## QR payload

The ESP32 generates a QR like:

```text
qroplate://connect?device=DEV-000001&mac=AA:BB:CC:DD:EE:FF&code=CHANGE_ME
```

The Flutter application will parse this custom URI, scan for the matching BLE device and connect to it.

## Build with PlatformIO

Open the repository in VS Code + PlatformIO and run:

```bash
pio run
pio run -t upload
pio device monitor -b 115200
```

The project currently targets `esp32dev`. If the exact MH-ET LIVE ESP32 board needs a different PlatformIO board id, change only the `board =` line in `platformio.ini`.

## RTC behavior

On first boot after RTC battery loss, the firmware initializes DS3231 from firmware build time. A later Flutter/admin implementation should synchronize RTC with trusted server time.
